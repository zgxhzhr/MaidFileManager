# Maid File Manager

> 本文件对应 **Fabric 26.1.2** 端（版本 1.7.0-snapshot）。六端共用同一份功能说明；26.1.2 与其它端的差异见文末「26.1 适配要点」。
> 
> **维护节奏**：本端（26.1.2）跟随车万女仆（TLM）本体的发布状态。**在 TLM 本体发布正式版之前，本端只做缺陷修复，不主动跟进新功能**；唯一例外是已发布的四端（Forge 1.20.1 / NeoForge 1.21.1 / Fabric 1.20.1 / Fabric 1.21.1）出现新功能时，会同步到本端以保持六端功能一致。

车万女仆档案（迁移）管理器（Maid File Manager）是一款 车万女仆 的附属模组，围绕两个核心功能：把你的女仆打包带走，以及管理与救援女仆的自动备份。

无论是换整合包重新开始，还是把单机养成的女仆带到服务器里，本模组都能让女仆数据在 1.20 / 1.20.1 / 1.21 / 1.21.1 之间自由迁移，并同时支持 Forge、NeoForge 与 Fabric 三大加载器。

> Fabric 版本基于社区非官方移植的 TLM，非车万女仆本体官方支持，如遇问题请先确认是否为移植版自身原因。

配套图文教程：<https://www.mcmod.cn/post/6715.html>

## 功能特性

- **一键导出/导入**：游戏内按 U 键唤出面板（可在「选项 → 控制设置 → 女仆档案管理」中改键），勾选女仆即可导出为 `.maid` 文件，勾选文件即可导入还原
- **批量操作**：支持同时选中多个女仆或文件，一键批量导出/导入
- **跨版本搬运**：1.20 ↔ 1.20.1 ↔ 1.21 ↔ 1.21.1 导出的 `.maid` 文件互相兼容，导入时自动完成数据迁移
- **药水效果跨版本迁移**：导出时同时保存原版 NBT（active_effects）与跨版本标准化（normalized）双份数据，导入时按目标版本自动恢复
- **药水效果恢复由服务端开关控制**：是否恢复只看配置项 `allow_effects`（1.6.3 起不再按效果 ID 白名单筛选）；万法皆通特殊女仆身上的永久效果由该模组自行维护，不受本开关拦截
- **饰品导入**：默认携带，可关闭；按「声明制」恢复饰品：只有主动声明可携带的命名空间才会随 `.maid` 迁移，车万女仆本体（`touhou_little_maid`）与万法皆通（`touhou_little_maid_spell`）为内置声明；未声明的命名空间一律丢弃并给出提示。跨版本同样保留属性：同版本走平台层完整物品 NBT 解析，1.20 → 1.21 走 DataFixerUpper 升级，1.21 → 1.20 走组件格式手动降级，附魔 / 耐久 / 无法破坏 / 基础数值等一并保留；仅在无法解析或来源版本未知时才回退为同类型全新饰品；目标世界缺注册物品时安全跳过
- **饰品导入设置（OP 管控）**：服务端可设「导入时丢弃饰品属性」（默认保留）与「禁用携带的饰品」清单，客户端进服自动同步、非 OP 只读；清单只列出真正的饰品（按车万女仆本体的饰品注册表判定，工具 / 材料 / 书籍不再混入），支持按名称或 ID 实时搜索；导入后逐件反馈处理结果（被丢弃 / 被还原为全新物品及原因），列表放不下的说明仍会完整送达聊天栏
- **进度导入**：默认携带，可配置是否还原女仆成就进度
- **导入后删除源文件**：导入 Tab 提供「导入后删除文件」开关（默认关闭），仅删除服务端确认生成成功的那批，失败文件原样保留
- **AI 对话数据迁移**：AI 人设（CustomSetting）、聊天历史（MaidHistoryChat，最多 512 条）、压缩摘要（MaidHistorySummary）、Token 用量跨版本完整迁移
- **安全防护**：导出时不保留背包与主副手物品，防止利用导出机制刷取物品
- **导入 UUID 确定性派生**：导入生成的女仆实体 UUID 不随机，而由「源女仆 UUID + 导入玩家 UUID」经 v3 名字 UUID 确定性派生（纯函数、无任何额外存储）——同一玩家对同一文件的任意次导入目标 UUID 恒定，不同玩家（多人服分享同一文件）因玩家 UUID 参与派生而各自独立、互不冲突。导入前做前置存活检测：源女仆仍存活于当前世界（已加载实体或 TLM 存活登记在册）时直接拒绝并给出含女仆名的明确提示，避免产生重复个体；导出时勾选移除会在实体移除前先清除其全部存活登记，因此「导出并移除后再导回」、原女仆已死亡、跨存档导入均可正常进行。女仆被收入魂符等容器时通常同样会因存活登记在册而被拦截；若某条容器路径未产生存活登记而放行，副本与容器内女仆 UUID 相同，容器将无法再放出，同样不能借此刷取
- **服务端统一导出**：仅 OP（权限等级 2）可用，按玩家分组导出到服务端 `maid_file/maid_exports/<玩家名>/`；只写文件、永不移除女仆；需每位玩家本人同意（默认不同意）
- **备份管理**：在档案管理器（按 U 唤出）标题栏的「备份」按钮或游戏主菜单入口打开，浏览车万女仆自动产出的备份并导出为 `.maid`；本机（单人世界 / 局域网主机）直接读取本机存档，游戏主菜单则合并展示本机所有存档的备份；专业服务器由服务端代读（服务端只读，不写、不删任何数据），OP（权限等级 2）可见全部玩家的备份、非 OP 仅见自己名下；导出文件一律落在客户端 `maid_file/maid_exports/<玩家名>/`
- **服务端配置同步**：联机宿主（OP）集中管控六项开关与饰品导入设置（丢弃属性 / 禁用命名空间清单 / 禁用 Curios 槽位清单 / 禁用携带清单），客户端进服自动同步、非 OP 只读
- **附属数据迁移 SPI**：对外提供统一迁移接口（`MaidMigrationProvider`），附属模组可自行注册，把不在女仆实体 NBT 上的数据（独立 SavedData / Capability / 玩家持久化数据 / 外部存储等）随 `.maid` 一起迁移；附属未加载时自动跳过、不报错。详见下文「附属模组接入」
- **属性迁移公平可信**：血量 / 攻击力基础值导入时无条件回归车万女仆按好感等级（含渡劫）计算的白板值，全局生物血量倍率类模组直接抬高的数值不随女仆跨存档迁移，保证联机导入公平；附属模组通过饰品 / 词条修饰符提供的合法加成在女仆入世界后自动恢复，满血女仆导入后不再掉血
- **无残留**：卸载模组不影响已导入的女仆

## 安装

1. 安装对应版本的 Forge / NeoForge / Fabric（Fabric 还需 Fabric API）
2. 安装 Touhou Little Maid（车万女仆）模组作为前置；Fabric 玩家请安装社区非官方移植版 TLM
3. 将本模组 JAR 放入 `.minecraft/mods` 文件夹
4. 启动游戏

## 构建（从源码）

```powershell
.\gradlew.bat :fabric:build --offline --no-daemon
```
产物：`fabric/build/libs/maid_file_manager-fabric-26.1.2-1.7.0-snapshot.jar`

## 使用方法

游戏目录（`.minecraft` 或整合包实例目录，与 `mods` 平级）下的 `maid_file/` 文件夹：

| 文件夹 | 用途 |
|---|---|
| `maid_file/maid_exports/` | 导出结果，按玩家名分子文件夹 `maid_file/maid_exports/<玩家名>/` |
| `maid_file/maid_imports/` | 导入来源，把要导入的 `.maid` 文件放这里（没有可手动新建） |
| `maid_file/photos/` | 女仆档案头像的候选图片，放入后在档案界面挑选（等比缩放、最长边不超过 512 像素，原图不超过 4 MB） |
| `maid_file/maid_photos/` | 档案头像图片库，模组按女仆 UUID 自动维护，请勿手动改动 |

> 旧版本散落在游戏根目录的 `maid_exports/`、`maid_imports/` 与 `config/maid_file_manager/photos/`，会在首次启动时**自动搬运并入** `maid_file/` 下，无需手动处理。

1. 按 U 打开面板，在「导出」Tab 点「刷新」（列表只显示周围 128 格内、由你驯服的女仆），勾选后点导出；默认「保留原女仆在世界」开启，导出只是备份
2. 把 `.maid` 文件从旧存档的 `maid_file/maid_exports/<玩家名>/` 复制到新存档的 `maid_file/maid_imports/`
3. 在「导入」Tab 点「刷新」，勾选文件后点导入；可勾选「导入后删除文件」（默认关闭）；女仆生成在玩家身边安全位置，实体 UUID 按「源女仆 + 导入玩家」确定性派生（同源同玩家恒定，不随机）
4. 点「打开导出文件夹」可直接打开输出目录（导入 Tab 对应打开 `maid_file/maid_imports/`）
5. 需要找回车万女仆的自动备份时，点档案管理界面标题栏的「备份」按钮，或点游戏主菜单左上角的「档案」按钮（详见下文「备份管理」一节）

## 服务端配置（OP 管控）

服务端配置由联机宿主（OP，权限等级 2）在设置界面中修改，客户端进服自动同步；非 OP 只读，无法修改，也无法通过导入请求绕过。六项开关中「导入时允许携带无敌状态」与「迁移 Curios 饰品（`carry_curios_baubles`）」**默认关闭（false）**、其余四项**默认开启（true）**；另有饰品导入设置四项：「丢弃饰品属性」开关 + 三张禁令清单（按命名空间 / 按 Curios 槽位 / 按物品名）：

| 配置项 | 默认 | 关闭 / 生效时效果 |
|---|---|---|
| 允许客户端导入女仆 | 开启 | 所有玩家的导入被拒绝 |
| 导入时允许携带饰品 | 开启 | 饰品被丢弃 |
| 导入时允许携带进度 | 开启 | 进度数据不写入 |
| 导入时允许药水效果 | 开启 | 关闭时一律不恢复任何药水效果（不再有白名单例外）；万法皆通特殊女仆的永久效果由该模组自行维护，不受此开关影响 |
| 导入时允许携带无敌状态（替身地藏） | 关闭 | 源女仆的无敌状态不迁移 |
| 导入时丢弃饰品属性 | 关闭（保留属性） | 有效时饰品还原为同类型全新物品，附魔 / 耐久等属性被丢弃 |
| 禁用携带的饰品清单 | 空（不限制） | 命中清单的饰品在导入时直接丢弃 |

玩家侧开关「允许服务端统一导出你的女仆」**默认不同意（false）**，需玩家本人开启后，OP 才能在统一导出中导出该玩家的女仆。

玩家取消勾选「保留女仆在原世界中」导出时，默认会弹出二次确认窗；在弹窗中勾选「不再提示」后该选择**仅对当前存档 / 服务器生效**（按存档分别记录，互不影响），也可随时在客户端设置中通过「当前存档」开关恢复确认。

「饰品导入设置」次级界面（位于设置 → 服务端设置区块）中的「导入时丢弃饰品属性」与「禁用携带的饰品」清单同样是**服务端配置，仅 OP 可改**，客户端进服自动同步、非 OP 只读；导入时由服务端读取这份配置并统一执行，客户端不上传，因此无法绕过。该清单只列出真正的饰品（按车万女仆本体的饰品注册表判定，工具 / 材料 / 书籍不再混入），支持按名称或 ID 实时搜索；导入后被丢弃或还原为全新物品的饰品会逐件反馈原因，列表放不下的说明仍会完整送达聊天栏。

### 服务端配置：按模组 / 按 Curios 槽位禁用携带（OP）

除"按物品逐条禁用"外，OP 还可从两个批量维度禁用（设置界面 → 饰品导入设置 → **按模组 / 槽位禁用…**）：

| 配置键 | 说明 |
|---|---|
| `bauble_blocked_namespaces` | 按**模组**（命名空间）禁用，如 `create,botania` —— **对女仆自带饰品栏与 Curios 槽位同时生效** |
| `bauble_blocked_curios_slots` | 按 **Curios 槽位**禁用，如 `ring,necklace` |
| `carry_curios_baubles` | 是否允许携带 **Curios 饰品**（默认关闭；即使开启，容器类槽位仍硬禁） |
| `allow_server_export` | 客户端配置：是否允许服务端统一导出你的女仆（默认关闭） |
| `ui_music` / `ui_music_volume` | 客户端配置：界面背景音乐开关与音量（默认开启 / 0.15） |

界面中可直接勾选模组、手输槽位名；硬禁槽位（`back` 等背包类 / 数据容器）显示为「永久禁止」且不可取消。
服务端对提交内容做字符集收窄校验（防客户端篡改）并广播同步给所有玩家。
界面操作（与本模组其它设置界面一致）：顶部三个标签 `按物品` / `按模组` / `按 Curios 槽位` → 搜索 → 底部 `上一页`/`下一页`/`完成`。其中 **`按物品` 是只读清单**（用来查看某个具体物品属于哪个命名空间/槽位），实际勾选在 `按模组` 与 `按 Curios 槽位` 两个标签进行；后两者可**点击整行**勾选/取消。

- **按物品**（只读）：列出**所有模组**中"可作为女仆饰品佩戴"的物品（判定走 TLM 饰品注册表，与游戏内饰品槽位校验同源），**不限于车万本体 / 万法皆通**；本标签仅用于查看，不支持在此勾选或取消，禁用在另外两个标签操作。
- **按模组**：列出整合包里**所有已加载模组**（不要求对方接入任何接口），每行标注 `已声明可携带`（已接入 `MaidBaubleCarrier`）或 `未适配·默认丢弃`。勾选＝禁用该模组饰品，对女仆自带饰品栏与 Curios 槽位同时生效。
- **按 Curios 槽位**：硬禁槽位（`back` 等）显示 `永久禁止` 且不可取消；其余槽位在搜索框输入名字后点 `添加` 加入禁用，点击已加入的行可移除。

### 整合包作者专用：饰品导入白 / 黑名单（bauble_import.json）

面向整合包作者，模组支持在 `config/maid_file_manager/bauble_import.json` 中以独立 JSON 文件预先规定允许 / 禁止携带的饰品：

- **存在即生效**：只要该文件存在且能解析为 JSON 对象，`blacklist`（黑名单）即在游戏内（含 OP）变为只读、命中即丢弃；`whitelist`（白名单）非空才生效，表示"仅允许清单内的饰品导入"，清单外一律强制禁用；
- **匹配粒度**：每条可用物品注册 ID 或物品中文显示名**精确匹配**（**不区分大小写**：清单装载时统一小写化，比较前同样归一化）；黑名单与 OP 在游戏内维护的禁用携带饰品清单取**并集**，白名单非空才生效，且仍受**已声明可携带的命名空间**约束（1.6.2 起为声明制，车万女仆本体与万法皆通只是内置声明，其它模组**只能**通过 `MaidBaubleCarrier` SPI 在代码级声明（**没有配置文件入口**，写进 `bauble_import.json` 不会生效））；
- **OP 仍可追加管控**：OP 可在游戏内额外勾选 / 取消禁用其它饰品（含白名单内的），这只影响 OP 自己的禁用清单（写入 `config/maid_file_manager-server.properties`），不会改动整合包的黑名单；
- **失败关闭**：文件存在但解析失败时，拒绝导入全部饰品并在日志输出 `ERROR`，绝不静默放行；
- OP 仍可修改「导入时丢弃饰品属性」开关，该开关不受本文件影响。

完整字段说明、判定顺序、示例与常见问题见根目录 [`饰品导入配置说明（整合包作者）.md`](饰品导入配置说明（整合包作者）.md)。

### 整合包作者专用：识别导入的女仆（maidfm_imported）

模组在**导入女仆时**，会往女仆实体的持久化标签写入一个标记 `maidfm_imported`（真值），供整合包作者在实体生成事件中识别「这只女仆刚由本模组导入产生」，从而对结构特殊女仆等场景发放补偿。

- **写入时机**：在女仆加入世界**之前**写入，早于实体生成事件；因此 KubeJS 的 `EntityEvents.spawned('touhou_little_maid:maid', ...)` 内可直接读到，不需要延迟到下一刻；
- **读取方式**：Forge / NeoForge 下落在实体 NBT 的 `ForgeData` / `NeoForgeData` 子标签，也就是 KubeJS 的 `entity.persistentData`，直接 `maid.persistentData.getBoolean('maidfm_imported')` 即可；Fabric 下落在实体根 NBT 的同名键；
- **随存档与文件迁移**：标记随女仆存档保存，导出 `.maid` 时一并带走，服务器重启、跨存档搬迁都不丢；
- **不会累积**：反复导入只会覆盖同一个键；且同一玩家对同一份文件的导入本身是幂等的（目标女仆 UUID 由源 UUID 与玩家 UUID 确定性派生），重复导入会先被模组的前置存活检测拦截（提示中带女仆名），漏网时再由服务端原生规则拒绝；
- **分不出来源**：`.maid` 文件不记录来源整合包，因此「从外部整合包导入」与「在本整合包内导出后又导入」无法区分，两者都会带上标记（后者的道具同样已在导出时剥离）。

最小接入示例（KubeJS）：

```js
EntityEvents.spawned('touhou_little_maid:maid', event => {
  const maid = event.entity
  if (!maid.persistentData.getBoolean('maidfm_imported')) return   // 只处理导入产生的女仆
  // 再按你自己的条件筛（例如结构女仆的固有 NBT 标记），随后发放补偿
})
```

## 服务端统一导出（仅 OP）

- **GUI**：导出 Tab 点「统一导出」进入统一导出模式（按钮变为「返回单独导出」），列表按玩家分组显示「▼ 玩家名（N 只女仆）」，未同意的玩家标注 [未同意导出]；提交后文件保存到服务端 `maid_file/maid_exports/<玩家名>/`
- **命令**：`/maidfile exportall` 一键导出所有已同意玩家的女仆（命令搜索半径 256 格；GUI 浏览列表搜索半径 128 格）
- 实体查找采用「直接取实体 → 128 格 AABB」两级查找（第三级「全维度 AABB」已在 1.6.4 移除：它对每个分区的实体逐个过谓词，配合一次最多 128×512 个 id 会被放大成主线程风暴）
- **范围限制**：只能导出每位玩家周围加载范围内、由其本人驯服的女仆；未加载区块、魂符/相片/胶卷等容器内的女仆无法覆盖。换服或灾备前请通知玩家把女仆带到身边

## 备份管理

除了手动导出，模组还提供「备份管理」界面，用于浏览车万女仆（TLM）自动产出的备份（`.dat`），并按需导出为本模组规范的 `.maid` 文件（命名规则与普通导出一致）。

**入口**

- 女仆档案管理界面（按 U 唤出）标题栏的「备份」按钮；
- 游戏主菜单左上角的「档案」按钮（tooltip：浏览并导出车万女仆的自动备份）。

**数据来源**

| 场景 | 备份位置 | 读取方式 |
|---|---|---|
| 单人世界 / 客户端发起的局域网联机 | 本机存档 | 客户端直接读取本机存档；从游戏主菜单进入时会合并展示本机所有存档的备份 |
| 专业服务端 | 服务器磁盘 | 向服务端请求代读（服务端只读，不写入、不删除任何数据） |

**权限**

- OP（权限等级 2）：可见、可导出全部玩家的备份；
- 非 OP：仅可见、仅能导出自己名下的备份。

**列表结构**：按「存档 → 玩家 → 女仆 → 备份文件」四层组织；专业服务端只持有当前存档的数据，顶层退化为单个「当前服务器」节点。玩家名解析：优先读取游戏目录下由 Minecraft 本体维护的 `usernamecache.json`（UUID 与用户名的对照表，正版与离线玩家登录过的名字都在其中），命中即用、不发起任何网络请求；未命中再对正版玩家走 Mojang 接口查询并本地缓存（每分钟最多查询一次）。玩家名也可在界面手动输入：先在对照表中按名字反查 UUID（因此正版玩家同样能匹配），未命中再按离线 UUID 规则匹配，匹配不上则继续显示 UUID。

**导出结果**：无论数据来自哪种场景，`.maid` 文件一律落在**客户端**的 `maid_file/maid_exports/<玩家名>/` 下；界面内「打开导出文件夹」按钮可直接打开该目录。

## 数据保留情况

| 数据 | 结果 |
|---|---|
| 主人驯服关系 | 保留（找不到原主人时生成为未驯服，用蛋糕重新驯服即可） |
| 名字 / 模型 | 保留（目标端缺模型时显示为博丽灵梦） |
| 血量 | 回归白板值。基础值无条件重置为车万女仆按好感等级计算的白板血量（满好感 80、渡劫 100），不保留源存档基础值——全局生物血量倍率类模组直接抬高的基础值不随女仆迁移，保证联机导入公平；持久修饰符迁移时随属性标签整体清除，附属合法的饰品 / 词条修饰符在女仆入世界 tick 后自动附加 |
| 攻击力 | 回归白板值。基础值无条件重置为车万女仆按好感等级计算的白板攻击力；附属通过饰品 / 词条修饰符提供的加成入世界后自动恢复 |
| AI 对话数据 | 保留（人设、聊天历史、摘要、Token 用量） |
| 饰品 | 默认保留，可关闭。**Curios 饰品默认不迁移**（1.6.2 起改为声明制，需模组主动声明命名空间）；容器类槽位（背包/箭袋/口袋/数据容器）无论是否声明都硬禁。同版本导入完整保留附魔 / 耐久 / 数据组件；跨版本导入经 DFU 升级（1.20 → 1.21）或组件格式降级（1.21 → 1.20）同样保留属性，仅在无法解析或来源版本未知时还原为同类型全新饰品；**未声明可携带的命名空间**下的饰品一律丢弃（声明制；车万女仆本体与万法皆通为内置声明）；命中「禁用携带」清单的饰品直接丢弃 |
| 药水效果 / 进度 | 默认保留，可分别关闭 |
| 无敌状态（替身地藏） | 默认不保留，可由服务端开关开启 |
| 背包与主副手物品 | 不保留（导出前请先取回） |
| 原 UUID / 着火、坠落等运行时状态 | 不保留（导入时生成新 UUID） |

## 附属模组接入（SPI）

本模组不针对任何具体附属做硬编码适配，而是对外提供统一的扩展接口：

- **数据迁移 SPI（`MaidMigrationProvider`）**：把**不在女仆实体 NBT 上**的数据（独立 `SavedData`、Forge Capability、玩家持久化数据、外部存储等，通常按女仆 UUID 关联）随 `.maid` 一起迁移；附属未加载时自动跳过、不报错。
- **饰品携带声明 SPI（`MaidBaubleCarrier`）**：女仆自带饰品栏与 Curios 槽位里的物品**默认不携带**，由各模组自行声明可携带的命名空间（可选槽位名单；容器类槽位硬禁）。

**完整接口说明**（方法签名、注册方式、接入示例、依赖姿势、安全约束、判定优先级、硬禁名单依据、二进制兼容承诺）见 **[《附属模组接口说明（模组作者）.md》](<附属模组接口说明（模组作者）.md>)**。

> 已经把数据写在女仆实体 NBT（含 `getPersistentData()` 与随存档自动序列化的 Capability）里的附属**无需接入**——本模组用 `EntityMaid#saveWithoutId` 导出完整女仆 NBT，这部分数据会自动随女仆迁移。

**修复 YSM（Yes Steve Model）换模女仆的名字显示。**

本版集中修掉**备份界面名字显示**的一整串问题，并给备份界面补了搜索与说明。

#### 新增

- **名字解析状态不持久**：模型名注册表此前只在内存。现在服务端注册表随存档持久化（重启不丢），客户端也会缓存从服务端学到的模型名（退到主界面走本地扫描时仍能显示）。

### v1.6.4

本版以**审查修复**为主，同时加入了 1.20.x 的**分片传输**能力（见下方条目）。

- **修复：重命名过的 `.maid` 会让客户端崩溃**。导入列表每帧解析文件名时间戳，原先 `substring` 前没有长度校验，遇到 `名字_20260820-15.maid` 这类文件名会抛越界异常；现在越界返回 0（列表时间显示 `?`），改名后的文件可正常导入。
- **修复：1.20.x 导入带头像的女仆会掉线**。1.20.x 的 C2S 载荷上限为 32767 字节；先加了本地预检（不再静默断连），随后由下方「分片传输」彻底解决——现在真联机也能导入带头像的档案。
- **修复：OP「统一导出」导出 0 条**。原先切换模式后立刻全选提交，此时主人映射尚未从服务端回包填充，请求玩家名为空导致全部跳过；现在等列表回包后再全选与提交，并保留真实回执。
- **导入所有权改为显式校验**：只允许导入本人导出的女仆，拒绝时给出明确提示（未驯服档案放行）。这是有意设计。
- **修复：1.21 → 1.20 导入的饰品属性静默丢失**（属性降级缺少 `AttributeName`、槽位键名错、`Operation` 类型错、UUID 格式错）。
- **修复：1.20.1 Forge 一次反射失败后，本次游戏内饰品全部无法恢复**（缓存被误标为已解析）。
- **修复：界面背景音乐对原版音乐压制过度**（最长静默约 20 分钟 → 每 10 tick 压一次），停止操作改回客户端主线程。
- **修复：配置列表超过 256 条时网络包错位 / 打开界面掉线**（写端计数与裁剪）。
- **修复：只读预览长文本打开即显示结尾；长背景故事在档案页掉帧**。
- **清理**：移除已无写入端的 `storeEffects` / `getStoredEffects` 半截接口。
- 文档：下载表、配置表、数据保留表更新；音乐版权声明去掉本机路径。
- **清理与健壮性补强**：配置解析（`properties` 非法转义、整合包 json 语法错误）不再导致启动失败；饰品禁用清单在 properties / `bauble_import.json` / 匹配三处统一小写归一化（此前手写带大写的条目会静默失效）；协议版本集中为 `MaidFilePackets.PROTOCOL_VERSION` 并补上 NeoForge 侧校验；三个界面在 `removed()` 中还原网络回调持有者（此前被 `setScreen` 切走时残留）；导出并移除女仆时同步删除 `maid_photos/<UUID>.png`；导入列表的时间列改为缓存格式化；移除死代码 `UiMusicManager.stopNow()`。
- **UI 交互契约修正**：二次确认弹窗支持「点击弹窗外部取消」，弹窗显示期间吞掉拖动/字符输入/非 ESC 按键（此前只吞点击与滚轮，背景控件仍会响应）；列表命中区从面板左右各 12px 收窄到 2px（此前可点到面板外）；档案页反馈提示 6 秒后自动消失（此前一直挂着）。
- **分片传输（1.20.x 大文件）**：1.20.x 原版对单个自定义包硬限 **32767 字节**，而带女仆头像的 `.maid` 通常 40~130 KB、档案照片可达 128 KiB。此前这类数据在**真联机**（独立服务器 / 远程服）下会直接断连，或只能被本地拒绝。
  现在新增分片通道，覆盖**导入**、**保存档案**、**导出**三条路径。**阈值按方向与端不同**：导出/下载方向与 1.20.x 的导入方向超过 **24 KiB** 即切分；1.21.x 的批量导入方向单包上限已放宽到 1 MiB，阈值取 1 MiB 减 1 KiB。接收端统一由 `ChunkedUploadAssembler` 重组（单片 24 KiB、单会话总量 8 MiB、最多 512 片、同时最多 8 个会话、60 秒超时回收）。
  注意：**单人世界 / 局域网主机的集成服务器**走内存直连，本来就不受该限制，仍走原路径。
- **导出并移除改为「客户端写盘回执后才删除」**：原先服务端发完包就 `discard()` 女仆并删头像，若客户端写盘失败（磁盘满 / 权限 / 路径异常）就会「女仆没了、文件也没有」。现在服务端只登记待删，等客户端 `export_write_ack` 确认落盘成功才删；写盘失败或客户端不回执则**永不删除**，女仆留在世界里等玩家重试。
- **备份列表扫描加上限**：服务端在主线程同步扫描备份目录，玩家/女仆目录极多时会明显卡顿；现限制每个维度最多 200 个目录并打 WARN，超出部分跳过。
- **Fabric 客户端网络包异常隔离**：28 个网络回调（17 个 C2S + 11 个 S2C）原先无 try/catch，解码异常会直接抛到网络线程；现统一包裹并记 ERROR，坏包只影响该条回包，不再牵连连接。
- **分片路径的两点行为差异**：① 不执行「导入后删除源文件」（该功能依赖逐项回传结果，分片路径未实现）；② 反馈走聊天栏而非界面回调。
- **档案照片源图上限 10 MB → 4 MB**：解码在客户端主线程同步执行，收紧上限以压缩选图时的卡顿（编码后仍受 128 KiB 限制，`.maid` 内嵌体积不变）。中英文提示文案同步更新。
- **协议维护性**：NeoForge 侧 23 处硬编码注册 ID 全部改为引用 `MaidFilePackets.ID_*` 常量；补齐 common 缺失的 `ID_SET_SERVER_BAUBLE_BLOCKED_LIST`；旧版单发协议的 3 个死通道（`export_maid` / `import_file` / `export_result`）在常量处标注为「兼容保留」。
- **协议版本 `PROTOCOL_VERSION` 升到 `"2"`**：`server_config_sync` 包追加了 `baubleWhitelistEnforced` 字段（修复「整合包配置解析失败时服务端全拒绝、客户端却显示可放行」的判定相反问题）。因此 **1.6.3 与 1.6.4 之间远程联机互拒**；单人世界不受影响，`.maid` 文件格式仍为 v7、两版本之间可互相导入导出。
- **NeoForge 端协议校验变更**：1.6.4 起 NeoForge 的 `registrar` 使用 `PROTOCOL_VERSION` 而非 1.6.3 里的 modid 字符串，同样导致 1.6.3 ↔ 1.6.4 在 NeoForge 端无法互连。
- **背景音乐更换为《与酒狐的旅行》**（BuShanDang，4:06，80 BPM，4/4，A 小调 → C 大调；作曲/作词 逐光星火-执火人，母带 −14.0 LUFS）：替换 1.6.3 的旧曲目。仍是**保留所有权利**的原创作品（(C) 2026 逐光星火-执火人），不适用 MIT 许可证，仅可随本模组原样分发，不得单独提取使用（详见《音乐版权声明》）。客户端音量配置 `ui_music_volume` 行为不变，默认 0.15。
兼容性：`.maid` 格式仍为 v7，旧文件照常导入；数据迁移 SPI 签名未变，附属模组无需重新构建。

##### P0：发布阻断（13 条逐条）

**第一轮（基线 1.6.3）**

1. **1.20.x 大档案导入必被踢线** — 1.20.x 的原版 `ServerboundCustomPayloadPacket` 硬限 **32767 字节**，而导入通道按 512 KiB 设计、整批塞进一个 C2S 包，既无预检也无分片。带内嵌头像的 `.maid` 序列化后必然超限 → 服务端直接断连且**不给任何回执**。
2. **OP「统一导出」必然导出 0 条，还误报成功** — 确认流程里切模式时清空了「女仆 → 主人」映射却保留了旧列表，导致所有请求的玩家名都是空串 → 服务端 `getPlayerByName("")` 全部跳过 → 导出 0 条，而界面仍显示「请求已发送」（真实回执被 15 秒抑制窗口改道到聊天栏）。
3. **改个文件名就让客户端每帧崩溃** — 导入列表每帧解析文件名时间戳，`substring` 无长度校验。把档案重命名成 `博丽灵梦_20260820-15.maid`（同时含 `_` 与 `-` 且 `-` 后不足 6 字符）后打开导入页 → `StringIndexOutOfBoundsException`，客户端崩溃。

**第二轮（基线 1.6.4 工作区）**

4. **非 OP 能执行 `exportall`** — NeoForge 先注册了无权限要求的 `maidfile` 根节点，再注册同名节点（带 OP 要求）。Brigadier 里先注册的子命令优先 → **OP 门槛实际丢失**（用 Brigadier 1.3.10 写最小程序实测确认，非推测）。
5. **1.20.x 保存带头像的档案必断线** — 保存路径把照片塞进单包，与第 1 条同族、另一条通道。
6. **交付的 jar 与源码、README 不符** — 发布目录里的四个 jar 是比当前源码早一轮的中间态构建，README 宣称的多条修复**不在交付物里**。

**第三轮**

7. **NeoForge 每次登录必断连** — 配置同步包编码端写 15 项就结束，解码端多读一个 `boolean` → 解码越界。该包**每次登录必发**，所以 NeoForge 分发包单机/联机都无法进入游戏。根因：加字段时只改了读端、漏了写端。

**第四轮**

8. **fabric-1.20.1 网络整体不可用** — 每个 C2S 包在编码前就被释放（buffer 生命周期用错），该端所有网络功能全废。
9. **neoforge 超过 24 KiB 的批量导入静默丢失** — 第三轮曾判定「无需修改」，本轮证明该结论错误：分片导入只收不分发。
10. **fabric-1.21.1「导出并移除」必坏** — `export_write_ack` 未注册 payload 编解码器 → 回执永远收不到。
11. **fabric 两端启动即崩** — 实机复现，进不了游戏（本轮最先修的一条）。

**第五轮**

12. **导出永不落盘却回报成功** — `writeMaidFile` 的原子改名 `Files.move` 被误并进了注释 → 文件写进临时名就结束。配合「导出并移除」= **女仆被删除、档案没有生成 = 永久丢失女仆**。（这是第四轮修复自己引入的回归。）

**第六轮**：本轮首次 **0 个 P0** —— 前五轮清完后未再发现发布阻断级缺陷（因此下一条编号为 13）。

**第七轮（审查窗口内修复）**

13. **语言文件尾逗号 → Minecraft 整份跳过语言表** — `zh_cn.json` / `en_us.json` 最后一个键带多余逗号，Gson 严格解析失败后 Minecraft **跳过整份语言文件**，全部界面显示 `maid_file_manager.gui.xxx` 这样的原始键名。该缺陷自第四轮提交引入，贯穿第五、六轮全部交付物。
