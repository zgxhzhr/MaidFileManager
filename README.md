# Maid File Manager

**车万女仆档案（迁移）管理器**（Maid File Manager）是一款 [Touhou Little Maid](https://github.com/TartaricAcid/TouhouLittleMaid)（车万女仆）的附属模组，核心功能只有一个：把你的女仆打包带走。

无论是换整合包重新开始，还是把单机养成的女仆带到服务器里，本模组都能让女仆数据在 1.20 / 1.20.1 / 1.21 / 1.21.1 之间自由迁移，并同时支持 Forge、NeoForge 与 Fabric 三大加载器。

> Fabric 版本基于社区非官方移植的 TLM，非车万女仆本体官方支持，如遇问题请先确认是否为移植版自身原因。

配套图文教程：<https://www.mcmod.cn/post/6715.html>

规范文档（随模组分发包一并提供，与本 `README` 同目录）：

- [`.maid` 文件格式规范](女仆文件格式规范.md)：`.maid` 格式的权威定义，产出方与读取方均应遵循
- [饰品导入配置说明（整合包作者）](饰品导入配置说明（整合包作者）.md)：`bauble_import.json` 的完整字段、判定顺序与示例

## 功能特性

- **一键导出/导入**：游戏内按 U 键唤出面板（可在「选项 → 控制设置 → 女仆档案管理」中改键），勾选女仆即可导出为 `.maid` 文件，勾选文件即可导入还原
- **批量操作**：支持同时选中多个女仆或文件，一键批量导出/导入
- **跨版本搬运**：1.20 ↔ 1.20.1 ↔ 1.21 ↔ 1.21.1 导出的 `.maid` 文件互相兼容，导入时自动完成数据迁移
- **药水效果跨版本迁移**：导出时同时保存原版 NBT（active_effects）与跨版本标准化（normalized）双份数据，导入时按目标版本自动恢复
- **万法皆通常驻 buff 保护**：禁药水模式下，按「效果 ID 命中白名单（11 种万法皆通结构女仆固定的永久常驻效果）+ Duration=-1」双条件判定，将常驻效果写入持久化标签保留，再次导出可恢复；不依赖女仆实体身份判定
- **饰品导入**：默认携带，可关闭；仅恢复车万女仆本体与万法皆通两个命名空间的饰品。跨版本同样保留属性：同版本走平台层完整物品 NBT 解析，1.20 → 1.21 走 DataFixerUpper 升级，1.21 → 1.20 走组件格式手动降级，附魔 / 耐久 / 无法破坏 / 基础数值等一并保留；仅在无法解析或来源版本未知时才回退为同类型全新饰品；目标世界缺注册物品时安全跳过
- **饰品导入设置（OP 管控）**：服务端可设「导入时丢弃饰品属性」（默认保留）与「禁用携带的饰品」清单，客户端进服自动同步、非 OP 只读；清单只列出真正的饰品（按车万女仆本体的饰品注册表判定，工具 / 材料 / 书籍不再混入），支持按名称或 ID 实时搜索；导入后逐件反馈处理结果（被丢弃 / 被还原为全新物品及原因），列表放不下的说明仍会完整送达聊天栏
- **进度导入**：默认携带，可配置是否还原女仆成就进度
- **导入后删除源文件**：导入 Tab 提供「导入后删除文件」开关（默认关闭），仅删除服务端确认生成成功的那批，失败文件原样保留
- **AI 对话数据迁移**：AI 人设（CustomSetting）、聊天历史（MaidHistoryChat，最多 512 条）、压缩摘要（MaidHistorySummary）、Token 用量跨版本完整迁移
- **安全防护**：导出时不保留背包与主副手物品，防止利用导出机制刷取物品
- **导入 UUID 确定性派生**：导入生成的女仆实体 UUID 不随机，而由「源女仆 UUID + 导入玩家 UUID」经 v3 名字 UUID 确定性派生（纯函数、无任何额外存储）——同一玩家对同一文件的任意次导入目标 UUID 恒定，不同玩家（多人服分享同一文件）因玩家 UUID 参与派生而各自独立、互不冲突。导入前做前置存活检测：源女仆仍存活于当前世界（已加载实体或 TLM 存活登记在册）时直接拒绝并给出含女仆名的明确提示，避免产生重复个体；导出时勾选移除会在实体移除前先清除其全部存活登记，因此「导出并移除后再导回」、原女仆已死亡、跨存档导入均可正常进行。女仆被收入魂符等容器时通常同样会因存活登记在册而被拦截；若某条容器路径未产生存活登记而放行，副本与容器内女仆 UUID 相同，容器将无法再放出，同样不能借此刷取
- **服务端统一导出**：仅 OP（权限等级 2）可用，按玩家分组导出到服务端 `maid_file/maid_exports/<玩家名>/`；只写文件、永不移除女仆；需每位玩家本人同意（默认不同意）
- **备份管理**：在档案管理器（按 U 唤出）标题栏的「备份」按钮或游戏主菜单入口打开，浏览车万女仆自动产出的备份并导出为 `.maid`；本机（单人世界 / 局域网主机）直接读取本机存档，游戏主菜单则合并展示本机所有存档的备份；专业服务器由服务端代读（服务端只读，不写、不删任何数据），OP（权限等级 2）可见全部玩家的备份、非 OP 仅见自己名下；导出文件一律落在客户端 `maid_file/maid_exports/<玩家名>/`
- **服务端配置同步**：联机宿主（OP）集中管控五项开关与饰品导入设置（丢弃属性 / 禁用携带清单），客户端进服自动同步、非 OP 只读
- **附属数据迁移 SPI**：对外提供统一迁移接口（`MaidMigrationProvider`），附属模组可自行注册，把不在女仆实体 NBT 上的数据（独立 SavedData / Capability / 玩家持久化数据 / 外部存储等）随 `.maid` 一起迁移；附属未加载时自动跳过、不报错。详见下文「附属模组接入」
- **属性迁移公平可信**：血量 / 攻击力基础值导入时无条件回归车万女仆按好感等级（含渡劫）计算的白板值，全局生物血量倍率类模组直接抬高的数值不随女仆跨存档迁移，保证联机导入公平；附属模组通过饰品 / 词条修饰符提供的合法加成在女仆入世界后自动恢复，满血女仆导入后不再掉血
- **无残留**：卸载模组不影响已导入的女仆

## 安装

1. 安装对应版本的 Forge / NeoForge / Fabric（Fabric 还需 Fabric API）
2. 安装 Touhou Little Maid（车万女仆）模组作为前置；Fabric 玩家请安装社区非官方移植版 TLM
3. 将本模组 JAR 放入 `.minecraft/mods` 文件夹
4. 启动游戏

## 使用方法

游戏目录（`.minecraft` 或整合包实例目录，与 `mods` 平级）下的 `maid_file/` 文件夹：

| 文件夹 | 用途 |
|---|---|
| `maid_file/maid_exports/` | 导出结果，按玩家名分子文件夹 `maid_file/maid_exports/<玩家名>/` |
| `maid_file/maid_imports/` | 导入来源，把要导入的 `.maid` 文件放这里（没有可手动新建） |
| `maid_file/photos/` | 女仆档案头像的候选图片，放入后在档案界面挑选（等比缩放、最长边不超过 512 像素，原图不超过 10MB） |
| `maid_file/maid_photos/` | 档案头像图片库，模组按女仆 UUID 自动维护，请勿手动改动 |

> 旧版本散落在游戏根目录的 `maid_exports/`、`maid_imports/` 与 `config/maid_file_manager/photos/`，会在首次启动时**自动搬运并入** `maid_file/` 下，无需手动处理。

1. 按 U 打开面板，在「导出」Tab 点「刷新」（列表只显示周围 128 格内、由你驯服的女仆），勾选后点导出；默认「保留原女仆在世界」开启，导出只是备份
2. 把 `.maid` 文件从旧存档的 `maid_file/maid_exports/<玩家名>/` 复制到新存档的 `maid_file/maid_imports/`
3. 在「导入」Tab 点「刷新」，勾选文件后点导入；可勾选「导入后删除文件」（默认关闭）；女仆生成在玩家身边安全位置，实体 UUID 按「源女仆 + 导入玩家」确定性派生（同源同玩家恒定，不随机）
4. 点「打开导出文件夹」可直接打开输出目录（导入 Tab 对应打开 `maid_file/maid_imports/`）
5. 需要找回车万女仆的自动备份时，点档案管理界面标题栏的「备份」按钮，或从游戏主菜单进入「备份管理」（详见下文「备份管理」一节）

## 服务端配置（OP 管控）

服务端配置由联机宿主（OP，权限等级 2）在设置界面中修改，客户端进服自动同步；非 OP 只读，无法修改，也无法通过导入请求绕过。五项开关中「导入时允许携带无敌状态」**默认关闭（false）**、其余四项**默认开启（true）**，另有饰品导入设置两项：

| 配置项 | 默认 | 关闭 / 生效时效果 |
|---|---|---|
| 允许客户端导入女仆 | 开启 | 所有玩家的导入被拒绝 |
| 导入时允许携带饰品 | 开启 | 饰品被丢弃 |
| 导入时允许携带进度 | 开启 | 进度数据不写入 |
| 导入时允许药水效果 | 开启 | 非白名单药水被丢弃；万法皆通 11 种常驻效果仍写入持久化标签中转保留 |
| 导入时允许携带无敌状态（替身地藏） | 关闭 | 源女仆的无敌状态不迁移 |
| 导入时丢弃饰品属性 | 关闭（保留属性） | 有效时饰品还原为同类型全新物品，附魔 / 耐久等属性被丢弃 |
| 禁用携带的饰品清单 | 空（不限制） | 命中清单的饰品在导入时直接丢弃 |

玩家侧开关「允许服务端统一导出你的女仆」**默认不同意（false）**，需玩家本人开启后，OP 才能在统一导出中导出该玩家的女仆。

玩家取消勾选「保留女仆在原世界中」导出时，默认会弹出二次确认窗；在弹窗中勾选「不再提示」后该选择**仅对当前存档 / 服务器生效**（按存档分别记录，互不影响），也可随时在客户端设置中通过「当前存档」开关恢复确认。

「饰品导入设置」次级界面（位于设置 → 服务端设置区块）中的「导入时丢弃饰品属性」与「禁用携带的饰品」清单同样是**服务端配置，仅 OP 可改**，客户端进服自动同步、非 OP 只读；导入时由服务端读取这份配置并统一执行，客户端不上传，因此无法绕过。该清单只列出真正的饰品（按车万女仆本体的饰品注册表判定，工具 / 材料 / 书籍不再混入），支持按名称或 ID 实时搜索；导入后被丢弃或还原为全新物品的饰品会逐件反馈原因，列表放不下的说明仍会完整送达聊天栏。

### 服务端配置：按模组 / 按 Curios 槽位禁用携带（OP）

除"按物品逐条禁用"外，OP 还可从两个批量维度禁用（设置界面 → 饰品导入设置 → **按模组 / 槽位禁用…**）：

| 配置键 | 说明 |
|---|---|
| `bauble_blocked_namespaces` | 按**模组**（命名空间）禁用，如 `create,botania` —— **对女仆自带饰品栏与 Curios 槽位同时生效** |
| `bauble_blocked_curios_slots` | 按 **Curios 槽位**禁用，如 `ring,necklace` |

界面中可直接勾选模组、手输槽位名；硬禁槽位（`back` 等背包类 / 数据容器）显示为「永久禁止」且不可取消。
服务端对提交内容做字符集收窄校验（防客户端篡改）并广播同步给所有玩家。
界面操作（与本模组其它设置界面一致）：顶部三个标签 `按物品` / `按模组` / `按 Curios 槽位` → 搜索 → **点击整行**勾选/取消 → 底部 `上一页`/`下一页`/`完成`。

- **按物品**：列出**所有模组**中"可作为女仆饰品佩戴"的物品（判定走 TLM 饰品注册表，与游戏内饰品槽位校验同源），**不限于车万本体 / 万法皆通**；整合包强制禁用的条目以只读勾选显示。
- **按模组**：列出整合包里**所有已加载模组**（不要求对方接入任何接口），每行标注 `已声明可携带`（已接入 `MaidBaubleCarrier`）或 `未适配·默认丢弃`。勾选＝禁用该模组饰品，对女仆自带饰品栏与 Curios 槽位同时生效。
- **按 Curios 槽位**：硬禁槽位（`back` 等）显示 `永久禁止` 且不可取消；其余槽位在搜索框输入名字后点 `添加` 加入禁用，点击已加入的行可移除。

### 整合包作者专用：饰品导入白 / 黑名单（bauble_import.json）

面向整合包作者，模组支持在 `config/maid_file_manager/bauble_import.json` 中以独立 JSON 文件预先规定允许 / 禁止携带的饰品：

- **存在即生效**：只要该文件存在且能解析为 JSON 对象，`blacklist`（黑名单）即在游戏内（含 OP）变为只读、命中即丢弃；`whitelist`（白名单）非空才生效，表示"仅允许清单内的饰品导入"，清单外一律强制禁用；
- **匹配粒度**：每条可用物品注册 ID 或物品中文显示名**精确匹配**（区分大小写）；黑名单与 OP 在游戏内维护的禁用携带饰品清单取**并集**，白名单非空才生效，且仍受允许命名空间（车万女仆本体 / 万法皆通）约束；
- **OP 仍可追加管控**：OP 可在游戏内额外勾选 / 取消禁用其它饰品（含白名单内的），这只影响 OP 自己的禁用清单（写入 `config/maid_file_manager-server.properties`），不会改动整合包的黑名单；
- **失败关闭**：文件存在但解析失败时，拒绝导入全部饰品并在日志输出 `ERROR`，绝不静默放行；
- OP 仍可修改「导入时丢弃饰品属性」开关，该开关不受本文件影响。

完整字段说明、判定顺序、示例与常见问题见根目录 [`饰品导入配置说明（整合包作者）.md`](饰品导入配置说明（整合包作者）.md)。

### 整合包作者专用：识别导入的女仆（maidfm_imported）

模组在**导入女仆时**，会往女仆实体的持久化标签写入一个标记 `maidfm_imported`（真值），供整合包作者在实体生成事件中识别「这只女仆刚由本模组导入产生」，从而对结构特殊女仆等场景发放补偿。

- **写入时机**：在女仆加入世界**之前**写入，早于实体生成事件；因此 KubeJS 的 `EntityEvents.spawned('touhou_little_maid:maid', ...)` 内可直接读到，不需要延迟到下一刻；
- **读取方式**：Forge / NeoForge 下落在实体 NBT 的 `ForgeData` / `NeoForgeData` 子标签，也就是 KubeJS 的 `entity.persistentData`，直接 `maid.persistentData.getBoolean('maidfm_imported')` 即可；Fabric 下落在实体根 NBT 的同名键；
- **随存档与文件迁移**：标记随女仆存档保存，导出 `.maid` 时一并带走，服务器重启、跨存档搬迁都不丢；
- **不会累积**：反复导入只会覆盖同一个键；且同一玩家对同一份文件的导入本身是幂等的（目标女仆 UUID 由源 UUID 与玩家 UUID 确定性派生），重复导入会先被模组的前置存活检测拦截（提示中带女仆名），漏网时再由服务端原生规则拒绝；
- **分不出来源**：`.maid` 文件不记录来源整合包，因此「从外部整合包导入」与「在本整合包内导出后又导入」无法区分，两者都会带上标记（后者的道具同样已在导出时剥离）。

最小接入示例（KubeJS）：

```js
EntityEvents.spawned('touhou_little_maid:maid', event => {
  const maid = event.entity
  if (!maid.persistentData.getBoolean('maidfm_imported')) return   // 只处理导入产生的女仆
  // 再按你自己的条件筛（例如结构女仆的固有 NBT 标记），随后发放补偿
})
```

## 服务端统一导出（仅 OP）

- **GUI**：导出 Tab 点「统一导出」进入统一导出模式（按钮变为「返回单独导出」），列表按玩家分组显示「▼ 玩家名（N 只女仆）」，未同意的玩家标注 [未同意导出]；提交后文件保存到服务端 `maid_file/maid_exports/<玩家名>/`
- **命令**：`/maidfile exportall` 一键导出所有已同意玩家的女仆（命令搜索半径 256 格；GUI 浏览列表搜索半径 128 格）
- 实体查找采用「直接取实体 → 128 格 AABB → 全维度 AABB」三级查找防漏
- **范围限制**：只能导出每位玩家周围加载范围内、由其本人驯服的女仆；未加载区块、魂符/相片/胶卷等容器内的女仆无法覆盖。换服或灾备前请通知玩家把女仆带到身边

## 备份管理

除了手动导出，模组还提供「备份管理」界面，用于浏览车万女仆（TLM）自动产出的备份（`.dat`），并按需导出为本模组规范的 `.maid` 文件（命名规则与普通导出一致）。

**入口**

- 女仆档案管理界面（按 U 唤出）标题栏的「备份」按钮；
- 游戏主菜单的「备份管理」入口。

**数据来源**

| 场景 | 备份位置 | 读取方式 |
|---|---|---|
| 单人世界 / 客户端发起的局域网联机 | 本机存档 | 客户端直接读取本机存档；从游戏主菜单进入时会合并展示本机所有存档的备份 |
| 专业服务端 | 服务器磁盘 | 向服务端请求代读（服务端只读，不写入、不删除任何数据） |

**权限**

- OP（权限等级 2）：可见、可导出全部玩家的备份；
- 非 OP：仅可见、仅能导出自己名下的备份。

**列表结构**：按「存档 → 玩家 → 女仆 → 备份文件」四层组织；专业服务端只持有当前存档的数据，顶层退化为单个「当前服务器」节点。玩家名解析：优先读取游戏目录下由 Minecraft 本体维护的 `usernamecache.json`（UUID 与用户名的对照表，正版与离线玩家登录过的名字都在其中），命中即用、不发起任何网络请求；未命中再对正版玩家走 Mojang 接口查询并本地缓存（每分钟最多查询一次）。玩家名也可在界面手动输入：先在对照表中按名字反查 UUID（因此正版玩家同样能匹配），未命中再按离线 UUID 规则匹配，匹配不上则继续显示 UUID。

**导出结果**：无论数据来自哪种场景，`.maid` 文件一律落在**客户端**的 `maid_file/maid_exports/<玩家名>/` 下；界面内「打开导出文件夹」按钮可直接打开该目录。

## 数据保留情况

| 数据 | 结果 |
|---|---|
| 主人驯服关系 | 保留（找不到原主人时生成为未驯服，用蛋糕重新驯服即可） |
| 名字 / 模型 | 保留（目标端缺模型时显示为博丽灵梦） |
| 血量 | 回归白板值。基础值无条件重置为车万女仆按好感等级计算的白板血量（满好感 80、渡劫 100），不保留源存档基础值——全局生物血量倍率类模组直接抬高的基础值不随女仆迁移，保证联机导入公平；持久修饰符迁移时随属性标签整体清除，附属合法的饰品 / 词条修饰符在女仆入世界 tick 后自动附加 |
| 攻击力 | 回归白板值。基础值无条件重置为车万女仆按好感等级计算的白板攻击力；附属通过饰品 / 词条修饰符提供的加成入世界后自动恢复 |
| AI 对话数据 | 保留（人设、聊天历史、摘要、Token 用量） |
| 饰品 | 默认保留，可关闭。同版本导入完整保留附魔 / 耐久 / 数据组件；跨版本导入经 DFU 升级（1.20 → 1.21）或组件格式降级（1.21 → 1.20）同样保留属性，仅在无法解析或来源版本未知时还原为同类型全新饰品；白名单（车万女仆本体与万法皆通）之外的饰品一律丢弃；命中「禁用携带」清单的饰品直接丢弃 |
| 药水效果 / 进度 | 默认保留，可分别关闭 |
| 无敌状态（替身地藏） | 默认不保留，可由服务端开关开启 |
| 背包与主副手物品 | 不保留（导出前请先取回） |
| 原 UUID / 着火、坠落等运行时状态 | 不保留（导入时生成新 UUID） |

## 附属模组接入（SPI）

本模组不针对任何具体附属做硬编码适配，而是对外提供统一的扩展接口：

- **数据迁移 SPI（`MaidMigrationProvider`）**：把**不在女仆实体 NBT 上**的数据（独立 `SavedData`、Forge Capability、玩家持久化数据、外部存储等，通常按女仆 UUID 关联）随 `.maid` 一起迁移；附属未加载时自动跳过、不报错。
- **饰品携带声明 SPI（`MaidBaubleCarrier`）**：女仆自带饰品栏与 Curios 槽位里的物品**默认不携带**，由各模组自行声明可携带的命名空间（可选槽位名单；容器类槽位硬禁）。

**完整接口说明**（方法签名、注册方式、接入示例、依赖姿势、安全约束、判定优先级、硬禁名单依据、二进制兼容承诺）见 **[《附属模组接口说明（模组作者）.md》](<附属模组接口说明（模组作者）.md>)**。

> 已经把数据写在女仆实体 NBT（含 `getPersistentData()` 与随存档自动序列化的 Capability）里的附属**无需接入**——本模组用 `EntityMaid#saveWithoutId` 导出完整女仆 NBT，这部分数据会自动随女仆迁移。

### v1.4.0
- **破坏性变更：饰品携带改为「声明制」**。女仆自带饰品栏与 Curios 槽位里的物品，只有**主动声明**可携带的命名空间才会随 `.maid` 迁移；未声明的一律丢弃并给出提示（此前 Curios 槽位是未做任何处理、整体跟随文件走，属于需要修复的行为）。车万女仆本体与万法皆通为内置声明，行为不变；**Curios 的背包类槽位（`back` 等）无论是否声明都禁止携带**（会连带背包内容，属复制风险）。附属模组实现 `MaidBaubleCarrier` 并调用 `MaidBaubleCarrierRegistry.register(...)` 即可声明——**只允许声明自己的命名空间**，越权声明会被拒绝并记录 WARN。服务端新增配置项 `carry_curios_baubles`（默认关＝Curios 饰品一律不迁移），可在设置界面（OP）修改。
- **饰品携带声明（`MaidBaubleCarrier`）接入要点**：实现接口并 `MaidBaubleCarrierRegistry.register(...)` 即可。`getId()` 的命名空间即"声明者身份"，`carriedNamespaces()` 只能声明自己的命名空间（越权声明会被拒绝并记 WARN）；文件本身不含授权，导入只认本地注册表。可选方法 `carriedCuriosSlots()`：**留空＝不限槽位**（该模组物品在任何非硬禁槽位都可携带）；**填入槽位名＝只允许这些槽位**（推荐给"槽位本身是有状态容器"的模组，未列出的槽位——含将来新增的——默认不带）。容器类槽位（`back`、`ionocraft_backpack`、`quiver`、`pocket_*` 等）与已核实的容器类/数据容器槽位（`klein_star`、`deep_learner`、`soul*`）无论是否声明都禁止携带。
- 新增：附属模组统一迁移接口 SPI（`MaidMigrationProvider` + `MaidMigrationRegistry`），附属可自行注册导出 / 导入自身数据；`.maid` 文件格式升级到 v5，新增 `extras` 字段（旧 v4 文件正常导入，向后兼容）
- 新增：同一女仆重复导入拦截。导入实体 UUID 不再随机，而由「源女仆 UUID + 导入玩家 UUID」经 v3 名字 UUID 确定性派生（纯函数，无任何额外存储，不会随导入次数增长）：同一玩家重复导入同一文件时目标 UUID 恒定，导入前在全维度已加载实体与 `MaidWorldData` 未加载索引中检测该 UUID，命中即拒绝并提示具体原因；不同玩家导入同一文件因玩家 UUID 参与派生而互不冲突（多人服分享文件不受影响）；原女仆死亡 / 被移除 / 跨存档导入不受影响。女仆被收入魂符（实体离线、索引不可查）时重复导入虽会成功，但魂符内女仆与副本同 UUID 无法再放出，不能借此刷取。`.maid` 新增 `source_maid_uuid` 字段，旧文件从实体根 NBT 的 UUID 键兜底解析
- 改进：血量 / 攻击力基础值导入时无条件回归车万女仆按好感等级（含渡劫）计算的白板值，不再保留源存档基础值——全局生物血量倍率类模组（直接改基础值或写持久修饰符）抬升的数值不再随女仆跨存档迁移，保证联机导入公平；附属通过饰品 / 词条修饰符提供的合法加成在女仆入世界后自动恢复
- 修复：满血且带饰品 / 词条血量修饰符的女仆导入后掉血。原因是固定延迟一次校准无法保证晚于所有附属附加修饰符；改为在入世界后的有界窗口（约 1 秒）内逐 tick 按当前最大血量校准，可追上任意时刻附加的修饰符
- 重构：Java 包名由 `com.example.maid_file_manager` 迁移为 `io.github.zgxhzhr.maidfm`（MOD ID 仍为 `maid_file_manager`，不影响 `.maid` 文件与存档）
